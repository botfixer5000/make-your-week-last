“Automation run rate limit exceeded” in Grok Bot: what it means and what to do

The short answer: this error means a routine run was refused before it started. Either your own routines went over Grok Bot's hourly limits, or, in a known issue, a limit shared by all Grok Bot routines was full even though you barely used it. The run isn't queued or retried, so you have to run it again.

What "Automation run rate limit exceeded" means

Grok Bot's help lists two hourly limits for routines (Cursor help: Routines):

  • All your routines together can run up to 300 times an hour.
  • Each single routine can run up to 200 times an hour.

A run past either limit fails with "Automation run rate limit exceeded". The same help page adds that some runs fail with this error "because of a limit all Grok Bot routines share, even when your own routines run less than that," calls it a known issue, and says engineers are working on a fix.

Either way, the important part is the same: a run that fails with this error isn't retried automatically. Whatever that run was supposed to do didn't happen.

Is it you or the shared limit?

Look at the exact message. Users posting on the Cursor forum in October 2026 quoted webhook errors that named a platform-wide count, like this:

{"success":false,"error":"Automation run rate limit exceeded: grok bot limit 18000 per minute, current_count=18001"}

A Cursor team member replied that "that number isn't a counter on your account. It's a shared limit across all Grok Bot routines on the platform," that heavy traffic elsewhere had filled it, and that there was nothing on the user's side to reset (Cursor forum).

A quick way to tell:

SignProbably
Message mentions a huge "per minute" number your routines couldn't reachShared limit
Your routines run a few times an hour or lessShared limit
One routine has a Slack "any message" trigger on a busy channel, or a webhook that fires in burstsYour own limit
Runs fail at a steady rate when that one routine is busy, and work when it's quietYour own limit

For scale: a routine on the shortest allowed schedule (every five minutes, the minimum gap per docs.x.ai) runs 12 times an hour. Schedules alone almost never reach 200 an hour. Event triggers can.

If your own routines hit the limit

  1. Find the busy one. Open each bot's details, then Routines on the Details tab. Look for Slack triggers on "any message," triggers that watch all of Slack, and webhooks called by another app.
  2. Narrow the trigger. Grok Bot's help says to "narrow its trigger or widen its schedule." For Slack, trigger on a mention of the bot, a specific phrase, or a reaction you add, in one channel. Ask the bot: "Edit your routine: [name]. Only trigger when you're mentioned in #[channel]."
  3. Batch the sender. If another app calls your webhook for every small event, have it send one call with a list instead.
  4. Rerun what failed. Use Test on the routine, or resend the webhook call.

This also saves usage. Every run spends from your weekly pool, and Grok Bot's help warns that a Slack trigger on a busy channel "can use a week of usage in a day." The weekly usage guide has the full runs-per-week table.

If it's the shared limit

You can't fix it from your account, but you can limit the damage:

  • Leave your routines alone. Pausing, recreating or rewriting a routine won't help with a platform-side limit.
  • Rerun anything important once things settle: Test, or ask the bot to do the work in chat.
  • Check the time. In that thread, Cursor staff said the problem had shown up during "roughly 12:00 to 17:00 UTC," so that's when retries matter most. Treat that as a pattern seen in October, not a rule.
  • Watch for updates. Grok Bot's help says it will update the Routines article when the shared limit no longer affects routines.

Webhook senders: retry the right way

When a webhook-triggered run is refused, the caller gets an HTTP 400 with this error, and the call isn't queued. Many retry policies treat a 400 as permanent and give up. Cursor's staff suggested treating a 400 whose error says "Automation run rate limit exceeded" as temporary and retrying with backoff, "for example after 1, 2, 5 and 10 minutes" (Cursor forum).

Remember that a 200 means Grok Bot accepted the call and started a run, not that the bot finished. Check the bot's chat for the result (Cursor help).

One more safeguard: write the routine so a repeat call is harmless. SpaceXSI's docs recommend making retries idempotent where possible (docs), for example "skip this row if the same ID is already in the log."

FAQ

Does this error use up my weekly usage?

Grok Bot's help doesn't say. What is clear: the refused run never started, so its work didn't happen, and the rerun spends usage like any other run.

Is Grok Bot down when I see this?

Not necessarily. Forum users reported this error while status.cursor.com showed everything operational (Cursor forum). Your bots may still answer normally in chat.

Can I ask support to reset my counter?

If it's the shared limit, there's nothing on your account to reset, according to the Cursor staff reply in the forum thread. If it's your own limit, narrowing the trigger is the fix.
